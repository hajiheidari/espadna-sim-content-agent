# راه‌اندازی محلی

این نسخه شامل موجودی، اسکلت ربات، برنامه‌ریز ماهانه، خروجی خصوصی قابل رهگیری و پیش‌نمایش HTML آزمایشی است. ارسال خودکار، انتشار کانال، تصویر نهایی مطابق قالب‌های مرجع و استقرار هنوز انجام نشده‌اند. هیچ سرویس پولی لازم نیست.

Python نسخهٔ ۳٫۱۱ یا بالاتر لازم است. در محیط مجازی نصب و تست کنید:

```sh
python -m venv .venv
# Activate the virtual environment using your operating system's command.
python -m pip install .
python -m unittest discover -s tests -v
espadna --db /private/espadna.db init --owner YOUR_NUMERIC_TELEGRAM_ID
espadna --db /private/espadna.db import /private/inventory.xlsx --actor YOUR_NUMERIC_TELEGRAM_ID --dry-run
espadna --db /private/espadna.db import /private/inventory.xlsx --actor YOUR_NUMERIC_TELEGRAM_ID
```

در ویندوز به جای مسیرهای نمونه از پوشه‌ای خصوصی بیرون مخزن استفاده کنید. پوشهٔ دیتابیس باید از قبل وجود داشته باشد. دستور init فقط برای دیتابیس بدون کاربر اجرا می‌شود؛ مالک از طریق نام کاربری یا اولین پیام ربات تعیین نمی‌شود.

برای اجرای اختیاری ربات، متغیر محیطی `TELEGRAM_BOT_TOKEN` را در محیط محلی تنظیم و سپس `espadna --db PATH bot` را اجرا کنید. توکن را در دستور ثبت‌شونده در تاریخچه، فایل مخزن یا گزارش خطا ننویسید. اجرای این دستور ربات را به تلگرام متصل می‌کند؛ توسعه و تست‌ها نیازی به توکن واقعی ندارند.

## نقش‌ها و فرمان‌ها

| نقش | دسترسی |
| --- | --- |
| owner | ورود اکسل، وضعیت فروش، محتوای مجاز، تعیین نقش |
| admin | ورود اکسل، وضعیت فروش، محتوای مجاز |
| viewer | فقط محتوای مجاز |

فرمان `/catalog` حداکثر ۱۰ مورد قابل انتشار را نشان می‌دهد؛ قیمت در هیچ نقش یا پاسخ ربات نمایش داده نمی‌شود. `/sale NUMBER available|reserved|sold` وضعیت تجاری را عوض می‌کند. `/role USER_ID owner|admin|viewer` و `/revoke USER_ID` مختص مالک‌اند. لغو دسترسی با نگهداری سوابق انجام می‌شود؛ تعیین دوبارهٔ نقش دسترسی را فعال می‌کند. آخرین مالک فعال قابل تنزل یا لغو نیست. فایل xlsx فقط از مالک/ادمین در چت خصوصی دریافت می‌شود. چت گروهی و کاربران ناشناخته یا غیرفعال رد می‌شوند.

## قرارداد ورود اکسل

- تمام شیت‌ها پردازش می‌شوند. عنوان‌ها با حذف فاصلهٔ اضافی و یکسان‌سازی ی/ک خوانده می‌شوند. ستون‌های لازم: «شماره دلخواه»، «نوع سیم کارت»، «وضعیت سیم کارت» یا «وضعیت سیم»، «قیمت»، «اپراتور».
- شرایط فروش و تمام ستون‌های ناشناخته کاملاً نادیده گرفته می‌شوند؛ ذخیره یا به خروجی منتقل نمی‌شوند.
- نوع: ۱ دائمی، ۲ اعتباری. وضعیت سیم: ۱ صفر به‌نام، ۲ صفر، ۳ به‌نام کارکرده. این وضعیت‌ها از available/reserved/sold جدا هستند.
- شماره باید متن باشد. ارقام فارسی/عربی به لاتین تبدیل و فقط فاصله‌ها حذف می‌شوند. نتیجه باید ۱۱ رقم با شروع 09 باشد. سلول عددی، شماره ناقص و فرمول رد می‌شود؛ صفر گم‌شده حدس زده نمی‌شود.
- اپراتور فقط از ستون صریح و مقادیر مجاز همراه اول/ایرانسل/رایتل پذیرفته می‌شود. مقدار خالی ناشناخته است و نمایش داده نمی‌شود. پیش‌شماره یا نام شیت منبع تشخیص اپراتور نیست. مقدار نامعتبر ورود را متوقف می‌کند. پاک شدن مقدار در فایل، تأیید قبلی اپراتور را نیز پاک می‌کند.
- قیمت داخلی رشتهٔ اعشاری دقیق و غیرمنفی است؛ حداکثر ۲۴ رقم بخش صحیح و ۶ رقم اعشار ورودی پذیرفته می‌شود. مقدار بزرگ‌تر یا نمای بسیار کوچک/بزرگ رد می‌شود و هیچ گردکردن خودکاری انجام نمی‌شود. واحد پول از فایل قابل اثبات نیست و تبدیل واحد انجام نمی‌شود. مقدار خالی، قیمت داخلی را خالی می‌کند. قیمت صفر با مقدار خالی متفاوت است.
- فرمول و خطای اکسل در ستون‌های مورد استفاده رد می‌شود. سقف فایل ۱۰ مگابایت، محتوای بازشده ۵۰ مگابایت، ۲۰هزار ردیف و ۱۰۰ ستون در هر شیت است.
- تکرار یکسان ادغام می‌شود؛ تکرار متناقض یا ردیف نامعتبر، کل عملیات را بدون تغییر موجودی متوقف می‌کند. پیام خطا فقط شمارهٔ ترتیبی شیت/ردیف دارد.
- هر ورود در تراکنش مستقل اجرا می‌شود. ورود مجدد دادهٔ یکسان revision را تغییر نمی‌دهد. فایل جدید فقط فیلدهای موجودی را به‌روزرسانی می‌کند، بدون حذف رکورد غایب و بدون بازنشانی فروش/رزرو. حالت full sync وجود ندارد.
- dry-run هیچ رکورد، batch یا لاگ جدید نمی‌نویسد. ورود موفق digest فایل، شمارش تغییرات، عامل و زمان را ثبت می‌کند؛ snapshot دادهٔ قبل/بعد در audit خصوصی می‌ماند.

## مرز محرمانگی

فقط `public_item` و `caption` مرجع ساخت محتوای عمومی‌اند. فیلدهای مجاز شماره، نوع، وضعیت سیم و اپراتور تأییدشده هستند. مورد فروخته‌شده یا رزروشده قابل تولید محتوا نیست. پیش‌نمایش HTML نیز مقادیر مجاز را دوباره اعتبارسنجی می‌کند. کانال آینده باید همین مرز را استفاده و قبل از ارسال وضعیت فعلی را دوباره بررسی کند. خروجی دانلودشده در برنامه قابل شناسایی و نامعتبر اعلام می‌شود؛ جلوگیری از ارسال دستی فایل ذخیره‌شده توسط شخص ممکن نیست.

دیتابیس، audit، پشتیبان‌ها و اکسل دارای دادهٔ حساس‌اند. آن‌ها را خارج از checkout و زیر مجوز دسترسی محدود سیستم‌عامل نگه دارید. SQLite به‌خودی‌خود رمزگذاری نمی‌کند. audit در سطح برنامه و trigger فقط الحاقی است؛ در برابر مالک فایل یا مدیر دیتابیس سند ضد‌دستکاری محسوب نمی‌شود. پشتیبان خصوصی را با SQLite backup API و آزمون بازیابی تهیه کنید. توکن افشاشده را در BotFather تعویض کنید.

هیچ فایل واقعی، شمارهٔ واقعی، نام مشتری یا توکن وارد تست‌ها نشده است. شناسه‌های شماره در تست‌ها مصنوعی‌اند. `.gitignore` مانع معمول ثبت فایل حساس است، اما جای بازبینی `git diff --cached` را نمی‌گیرد. پیش از انتشار، فهرست فایل‌ها و محتوای staged را بازبینی کنید.

## محدودهٔ نسخه

schema نسخهٔ ۲ هنگام اتصال ساخته می‌شود و دیتابیس نسخهٔ ۱ در تراکنش قفل‌شده، بدون حذف موجودی و audit ارتقا می‌یابد؛ نسخهٔ ناشناخته رد می‌شود. ربات polling، حد دانلود اولیه و محدودیت parser دارد؛ صف پردازش، سهمیهٔ کاربران و بررسی فایل در فرایند جدا برای سرویس تولیدی هنوز لازم است. ربات عمداً اسکلت است و ورود فایل در همان فرایند انجام می‌شود. برای این مرحله هیچ شبکهٔ تلگرام واقعی، انتشار عمومی یا استقرار اجرا نشده است.

## آماده‌سازی ماهانه و رهگیری خروجی‌ها

```sh
espadna --db /private/espadna.db plan 2026-11 --actor OWNER_ID
espadna --db /private/espadna.db plan-status PLAN_ID --actor USER_ID
espadna --db /private/espadna.db plan-approve PLAN_ID --actor ADMIN_ID
espadna --db /private/espadna.db plan-export PLAN_ID --actor USER_ID --output /private/november.json
espadna --db /private/espadna.db export-alerts --actor USER_ID
espadna --db /private/espadna.db plan-refresh PLAN_ID --actor ADMIN_ID
espadna --db /private/espadna.db plan-preview PLAN_ID 2026-11-01 --actor USER_ID --output /private/day.html
```

ماه ورودی میلادی و در بازهٔ ۲۰۰۰ تا ۲۱۰۰ است. هر روز شش شمارهٔ متمایز از موجودی available انتخاب می‌شود؛ تکرار در روزهای مختلف مجاز است. حداقل شش شمارهٔ قابل فروش لازم است؛ در کمبود موجودی، برنامه ساخته/بازسازی نمی‌شود. برای هر ماه فقط یک برنامه وجود دارد. برنامه ابتدا draft است و owner/admin باید آن را تأیید کند. فرمان‌های معادل ربات: `/plan YYYY-MM`، `/planstatus ID`، `/approve ID`، `/refresh ID`، `/alerts`.

خروجی زمان هدف 08:00 در Asia/Tehran را با offset زمانی صحیح ذخیره می‌کند؛ این کار زمان‌بندی اجرایی یا ارسال نیست. شناسه‌های ۱ تا ۳۰ صرفاً جای رزروشدهٔ قالب در پنج گروه شش‌تایی‌اند. تأیید برنامهٔ موجودی به معنی تأیید طراحی بصری نیست. پیش‌نمایش فعلی یک چیدمان آزمایشی مشترک با متن‌های مستقل و ابعاد ۱۰۸۰×۱۹۲۰ است؛ برای ساخت ۳۰ ترکیب نهایی، تصویر مرجع تأییدشده لازم است.

هر تغییر revision موجودی، حتی قیمت داخلی، برنامهٔ وابسته را محافظه‌کارانه stale می‌کند. `plan-status` ممکن است state تأییدشده نشان دهد اما ready=false باشد؛ معیار آمادگی، ready و stale_slots است. ساخت خروجی/پیش‌نمایش، موجودی را دوباره در یک تراکنش بررسی می‌کند و برنامهٔ تأییدنشده یا stale را رد می‌کند. refresh شمارهٔ فروخته‌شده/رزروشده را جایگزین و برنامه را draft می‌کند؛ تأیید دوباره لازم است.

خروجی JSON شناسه و digest دارد و نسخهٔ برنامه و موجودی در دیتابیس خصوصی ثبت می‌شوند. `/alerts` یا `export-alerts` خروجی‌های قدیمی نامعتبر را نشان می‌دهد؛ viewer فقط خروجی‌های خودش و owner/admin همه را می‌بینند. هشدار در این مرحله هنگام درخواست کاربر خوانده می‌شود؛ اعلان خودکار ارسال نشده است. بازسازی و تأیید برنامه، فایل قدیمی را دوباره معتبر نمی‌کند. digest برای مقایسهٔ تمامیت فایل است؛ وضعیت معتبر بودن باید با دیتابیس زنده سنجیده شود. مسیر JSON و HTML باید خارج از checkout گیت باشد و فایل موجود بازنویسی نمی‌شود. فایل پیش‌نمایش HTML، خروجی ثبت‌شدهٔ دانلود محسوب نمی‌شود و فقط برای بازبینی است.

هر فرستندهٔ آینده باید درست قبل از ارسال از `approved_payload` استفاده کند، نه از JSON/HTML قدیمی. هنوز صف ارسال، قفل ارسال، ثبت موفقیت/خطای شبکه، idempotency تحویل و اصلاح پست کانال پیاده نشده است. بنابراین این نسخه مجوز اتصال مسیر خودکار به کانال تولیدی نیست.
